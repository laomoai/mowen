# 墨问应用级版本设计

## 产品边界

- 笔记以单篇笔记为版本对象。
- 表格以整张表的数据集为版本对象，不在单行详情中暴露单行历史入口。
- 第一版只恢复表数据（行与单元格值），不恢复列结构、字段配置、视图和图表配置。

## 表格版本：增量变更日志

每次新增、修改、删除、批量新增或整表恢复，都在同一 SQLite 事务中记录本次受影响行的 `before_rows` 和 `after_rows`，然后递增整表版本号。

这不是每次复制整张表：日常修改一行时只多写入该行的前后值，所以对写入延迟和存储的影响可控。查看旧版或恢复时，才从当前数据逆向应用后续变更，重建目标时点的整表状态。

### 系统表

- `_table_revision_heads(team_id, table_name, current_version)`：整表当前版本号。
- `_table_revisions`：版本号、操作类型、受影响记录 ID、前后行 JSON、操作人/鉴权来源、恢复来源和时间。

现有表首次发生数据变更时惰性建立 v1 基线，不需要一次性复制所有表。

## 差异与恢复

- 表格工具栏的“历史版本”显示整表时间线。
- 选中版本后，按记录显示“当前新增 / 当前已删除 / 内容有变化”，并继续展示字段级前后值。
- 整表恢复需要 `base_version`，如果查看历史后又有人改表，返回 `409 VERSION_CONFLICT`。
- 恢复前的整表状态会作为新版本保留，因此恢复本身可撤回。

## API

- `GET /api/tables/:tableName/revisions`
- `GET /api/tables/:tableName/revisions/:revisionId`
- `POST /api/tables/:tableName/restore-version`
- 笔记仍使用 `GET /api/notes/:id/revisions` 和 `POST /api/notes/:id/restore-version`。

历史查询继承表格读权限，恢复继承表格写权限；所有查询强制带 `team_id`，`scope=groups` 只能查看和恢复授权表。

## 验收要点

1. 修改 A、新增 B、删除 C 后，整表历史能同时显示三类差异。
2. 恢复到旧版后，A/B/C 都回到该时点的状态，总行数同步正确。
3. 恢复后可再恢复到操作前状态。
4. 普通 Web/API 写入、AI 助手写入、删除和回收站恢复都会记入整表版本。
5. 版本写入和业务写入位于同一事务，任一失败时不留半成品。
